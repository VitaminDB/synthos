# Gemma-4 26B A4B в synaptix (сентябрь 2026)

Модель: [`google/gemma-4-26B-A4B-it`](https://huggingface.co/google/gemma-4-26B-A4B-it)
— MoE на 25.2 млрд весов, из которых на токен работают 3.8 млрд (8 активных
экспертов из 128 плюс всегда активный плотный MLP). Текст + картинки, окно
контекста 256k, словарь 262k.

Бандл: `~/Storage/syn_models/gemma-4-26b-a4b-it.syn`, 18 ГБ — эксперты и
плотные MLP упакованы в NVFP4, внимание, эмбеддинги и башня зрения остались
BF16. Исходный HF-каталог — `~/models/google/gemma-4-26B-A4B-it` (49 ГБ),
нужен только для снятия эталона.

## Что в архитектуре нового

Текстовая башня легла на общий декодер (`synaptix-llm-common`), но
потребовала расширить его профиль — всё новое собрано в
`DecoderConfig::ext` (`DecoderExt`), и модели без него идут прежним путём.

**Послойная геометрия внимания.** Слои чередуются 5 sliding : 1 global
(окно 1024, global — каждый шестой, последний слой всегда global). Раньше
общий декодер считал, что голова у всех слоёв одна; у Gemma-4 это не так:

| | sliding (25 слоёв) | global (5 слоёв) |
| :---- | :---- | :---- |
| голов Q | 16 | 16 |
| размер головы | 256 | **512** |
| KV-голов | 8 | **2** |
| матрица V | своя | **нет — это выход `k_proj`** |
| RoPE | обычный, θ = 10⁴ | **proportional**, θ = 10⁶ |

`attention_k_eq_v` значит буквально следующее: значения берутся из той же
проекции, что и ключи, но снятой ДО Q/K-нормы и RoPE. В HF это видно по
порядку присваиваний (`value_states` держит ссылку на дорезанный тензор,
а `key_states` переприсваивается) — легко прочитать наоборот и получить
связный, но неверный ответ.

**Proportional RoPE.** На global-слоях вращается только четверть головы
(`partial_rotary_factor = 0.25`), но пары измерений берутся от ПОЛНОЙ головы
(HF `rotate_half` делит 512 пополам). Поэтому в терминах `RopeCache` это не
partial-RoPE, а обычный RoPE на всю голову с обратными частотами
`[θ^(-2j/512) для j < 64, дальше нули]`: нулевая частота даёт cos = 1,
sin = 0, то есть тождество. Считает это `Gemma4Config::proportional_freqs`.

**MoE рядом с плотным MLP, а не вместо него.** Плотный MLP (ширина 2112) —
всегда активный эксперт, MoE-ветка (128 экспертов по 704) считается от того
же входа ПАРАЛЛЕЛЬНО, и у каждой ветки свои нормы:

```
r  = вход FFN-части блока
h1 = post_feedforward_layernorm_1( mlp( pre_feedforward_layernorm(r) ) )
h2 = post_feedforward_layernorm_2( moe( pre_feedforward_layernorm_2(r) ) )
out = r + post_feedforward_layernorm(h1 + h2)
out = out * layer_scalar
```

Роутер смотрит на `r` — вход блока ДО pre-нормы MLP, — со своей нормой без
веса и множителем `router.scale · hidden^-1/2`. Множитель свёрнут в вес
нормы (`MoeSide::router_norm`), поэтому в `MoeFfn` уходит обычная
RMS-норма; для этого у `MoeFfn` появился `forward_routed` с отдельным входом
роутера. После нормировки top-k веса домножаются на
`router.per_expert_scale[e]` — это `MoeConfig::per_expert_scale`.

**Мелочи, каждая из которых ломает вывод молча:**

* RMS-нормы Gemma-4 хранятся БЕЗ сдвига `1 +` (в Gemma-3 был со сдвигом) →
  `NormGain::Plain`;
* масштаба `1/sqrt(d)` у внимания нет вовсе (`scaling = 1.0`) — его роль
  играет обучаемая Q-норма;
* поверх V идёт RMS-норма БЕЗ обучаемого веса;
* активация экспертов — `gelu_tanh`, а не `silu` (фьюз
  `silu_mul_quant_nvfp4` для них отключён);
* `final_logit_softcapping = 30`;
* стоп-токен «конец хода» (`<turn|>`, id 106) лежит только в
  `generation_config.json`. Без него модель дописывает следующий ход:
  «Столицей Франции является Париж.Столицей Франции является Париж.»

## Башня зрения

Не тайлы и не квадрат: картинка масштабируется с сохранением пропорций так,
чтобы патчей (16×16) было не больше бюджета, а обе стороны делились на
`pooling_kernel_size · patch_size = 48`. Бюджет — `max_soft_tokens · 9`, где
`max_soft_tokens ∈ {70, 140, 280, 560, 1120}` (по умолчанию 280).

Дальше: патчи → `2·(p − 0.5)` → линейная проекция в 1152 → плюс ДВЕ таблицы
позиционных эмбеддингов (отдельно по x и по y) → 27 слоёв двустороннего
внимания с двумерным RoPE (половина головы вращается позицией по x, половина
— по y; частоты считаются от `head_dim / 2`) → усреднение блоками 3×3 →
`× sqrt(1152)` в F32 → стандартизация `(h − std_bias) · std_scale` →
RMS-норма без веса → проекция в 2816.

В промпт блок картинки встаёт как `<|image>` + `<|image|>` × мягкие токены +
`<image|>`, а внутри прогона заполнителей внимание текстовой башни
ДВУСТОРОННЕЕ (`use_bidirectional_attention = "vision"`). Для этого у общего
декодера появился `forward_from_hidden_spans`: участки задаются абсолютными
позициями и переживают разрез префилла на чанки; flash на таких слоях
выключается, маска строится в `build_mask`.

Ресайз у нас билинейный, у HF — бикубический с антиалиасингом. Точного
совпадения тут нет (как и у остальных vision-башен движка).

## Скорость декода

`cargo test -p synaptix --release --test gemma4_decode_bench` — 64 токена по
одному промпту, разные раскладки точности. Профиль (`SYN_DECODE_PROF=1`)
включать только для разбора: он синхронизирует поток на каждой операции и
сам замедляет декод в полтора раза.

| внимание | голова | ток/с | чтение весов | текст |
| :---- | :---- | ----: | ----: | :---- |
| BF16 | BF16 | 76 | 4.8 ГБ/ток | чисто |
| BF16 | NVFP4 | 82 | 3.7 ГБ/ток | чисто |
| **MXFP8** | **MXFP8** (профиль по умолчанию) | **83** | 3.1 ГБ/ток | чисто |
| MXFP8 | NVFP4 | 85 | 2.7 ГБ/ток | чисто |
| NVFP4 | NVFP4 | 90 | 2.1 ГБ/ток | ломаются отдельные слова |

С графовым декодом (см. ниже) те же профили давали **97 ток/с** против 83–85,
после работы по ядрам (09.09) — **210 ток/с**.

**Внимание в MXFP8, а не в NVFP4.** Четырёх бит проекциям внимания не
хватает: в ответе воспроизводимо ломаются отдельные слова — «в уютном угpду»
вместо «в уютном углу», одинаково при обеих головах, на трёхстах токенах
ровно один такой сбой. Восемь бит текст держат, а скорость почти та же
(85 против 90): декод упирается в запуски ядер, а не в чтение весов. Против
плотного BF16 это плюс 7 ток/с и минус 1.6 ГБ VRAM. `optimal_profile` для
Gemma-4 ставит `attn_storage = MXFP8`.

### Что было сделано ради этих цифр

Первый замер давал 35 ток/с при потолке по памяти в 167. Разбор
(`decode_prof_report_and_clear`) показал, что упирается не в пропускную
способность, а в запуски ядер:

1. **Sliding-слои уходили в sdpa.** `narrow` по оси времени даёт
   нераскладываемый вид, flash отвечал `NonContiguous`, и на каждый слой
   каждого токена приходились `repeat_kv` (аллокация плюс broadcast) и
   полтора десятка запусков — 0.28 мс на слой при 0.02 мс работы. Теперь
   декод читает предвыделенный KV device-ядром (`flash_attention_dev` /
   `flash_attention_window_dev`), длина едет device-скаляром. Оконное ядро
   умело только голову 128 — добавлены инстанциации на 256
   (`flash_splitq_{f16,bf16}_hd256_win_dev`). Слой: 0.28 → 0.03 мс.
2. **MoE считала экспертов по одному.** Батчевый путь (`gemv_batched`)
   отключался, если у слоя нет кэша экспертов, — а у резидентной MoE его и
   нет. Плюс он требовал фьюза `silu_mul_quant_nvfp4`, которого для gelu не
   существует. Теперь батч работает и на резидентных экспертах, а для gelu
   активация с квантованием считаются отдельными ядрами — всё равно один
   проход на слой, а не на эксперта. Слой: 0.47 → 0.18 мс.
3. **Голова читалась плотной.** При связанных эмбеддингах квант головы
   игнорировался: словарь 262k в BF16 — это 1.5 ГБ чтения на каждый токен.
   Теперь плотный эмбеддинг остаётся для gather'а, а голова квантуется
   отдельной копией. Токен: 1.72 → 0.50 мс (NVFP4).
4. **Маска на одном запросе.** Срез `[att_lo, att_len)` уже обрезан и
   причинностью, и окном — строить маску на хосте и везти её на карту незачем.

## Графовый декод

Шаг декода захватывается в CUDA-граф целиком, **вместе с MoE**: 97 ток/с
против 83 обычным путём (+15 %). Мешало ровно одно — выбор экспертов ехал на
хост, а под захватом графа синхронизация нелегальна. Что для этого появилось:

* `nvfp4_expert_ptr_gather` — ядро собирает массивы указателей пакетного GEMV
  из ФИКСИРОВАННОЙ таблицы адресов экспертов по индексам НА КАРТЕ. Таблица
  (`ExpertTable` в `synaptix-core`) строится один раз на загрузке: адреса
  перемешанных копий стабильны, их же теперь строит `MoeFfn::load`;
* `MoeFfn::forward_dev` — весь шаг MoE на карте: логиты роутера, `topk_rows`,
  софтмакс по k, `per_expert_scale` (гейтер — `embed_gather`, а НЕ
  `index_select`: тот тащит индексы на хост), два индексируемых GEMV,
  взвешивание и сумма. Сверено с обычным путём **бит в бит**
  (`moe_ffn_cuda.rs::dev_path_matches_host_path`);
* `DecodeState` держит по паре RoPE-таблиц на тип слоя — у Gemma-4 sliding и
  global вращаются разными базами И разной шириной головы;
* device-путь внимания научился `attention_k_eq_v` и норме V без веса;
* `forward_decode_dev` считает MoE-ветку и `layer_scalar`.

Готовность проверяет `DecoderModel::graph_decode_ready` (все MoE-слои умеют
device-путь, блоки резидентны, sliding на ring-KV) плюс
`Gemma4Pipeline::graph_decode_supported`. Последний спрашивает про KV не
политику, а факт (`kv_all_dense`): профиль по умолчанию просит MXFP8, но
Gemma-4 его не получает ни на одном слое, и графу это не мешает. Голова в
MXFP8 тоже не мешает — её скретчи прогреваются тремя прогонами до захвата.

Совпадения токен в токен с обычным путём не бывает и не требуется: пути
считают одно и то же разными ядрами (слитая пара add+norm против двух
запусков), и greedy-цепочка расходится на ничьих. Критерий тот же, что у
существующего `cuda_graph_decode.rs`, — косинусная близость логитов одного
шага (0.9977) и совпадение argmax.

На этом месте (08.09) было 97 ток/с; дальше — работа по ядрам, см.
следующий раздел.

## Ядра декода: 97 → 210 ток/с (09.09)

Профиль снимался не хостовым `SYN_DECODE_PROF` (он синхронизирует поток на
каждой операции), а `nsys profile --cuda-graph-trace=node` по замеру
`decode_cuda_graph`: экспорт в sqlite и группировка ядер внутри графа по
именам. Первый же срез перевернул гипотезу «690 запусков на токен»: в графе
было **2215 ядер плюс 1890 узлов memset** на токен, занятость GPU 7.3 мс из
10.3, а оставшееся — промежутки между узлами. Самые массовые ядра — не
GEMV, а нормы (301 на токен), cast'ы bf16↔f16 (472), квантования (266) и
memset'ы почти под каждым выходом. Дальше по шагам, каждый со сверкой
(`gemma4_smoke` с иголкой, `graph_step` с cos логитов, Qwen3.8/Muse без
регресса):

| шаг | что сделано | ток/с |
| :---- | :---- | ----: |
| — | графовый декод, старт | 97 |
| A | выходы горячих операций без обнуления (`alloc_uninit`): ядра пишут их целиком, memset-узлы ушли | 125 |
| B | квант-проекции читают и пишут BF16 сами (`-DSYN_IN_BF16` / `-DSYN_OUT_BF16` у MXFP8-кванта и GEMV, NVFP4 умел); QLinear без обхода через F16 | 133 |
| C | слитые ядра слоя: хвост после внимания, хвост FFN, geglu+квант, подготовка внимания; групповые GEMV q/k/v и gate\|up со split-K; индексный GEMV экспертов без ptr_gather с эпилогом взвешенной суммы | 168 → 190 |
| D | flash-decode с GQA (K/V один раз на группу голов, MXFP8-квант входа `o_proj` в merge); логиты роутера — хвостовыми блоками GEMV gate\|up, top-k — блоком geglu | 199 → 210 |
| E | профиль фасада: BF16-счёт, BF16-эмбеддинги, голова NVFP4 — слитый путь дошёл до приложения | фасад 118 → 186 |

Итог: **4.75 мс/ток, 210 ток/с**. Чтение на токен в конфигурации замера
(MXFP8-внимание, NVFP4-эксперты, плотный MLP и голова, f32-роутер) — 2.7 ГБ,
то есть потолок при 800 ГБ/с — 292 ток/с; с головой MXFP8 (профиль по
умолчанию) — 3.1 ГБ и 261. В графе
399 ядер на токен, занятость 4.37 мс из 4.94: GEMV — 3.5 мс (80 %), всё
остальное — 0.85 мс, промежутки — 0.57 мс.

**Что живёт где.**

* `synaptix-core::tensor::decode_fused` — Tensor-обёртки слитых операций
  (выходы uninit, у NVFP4-пар пишется только строка 0 масштабов: GEMV
  хвост 128-тайла не читает); методы `Backend::dec_*`.
* `cu/fused/llm_decode.cu` — `dec_attn_tail` (пост-норма + residual + нормы
  входов MLP/экспертов/роутера с NVFP4/bf16-эпилогами), `dec_ffn_tail`
  (пост-нормы веток, сумма, пост-норма MLP, residual, `layer_scalar`, норма
  входа следующего слоя с MXFP8-эпилогом), `dec_geglu_quant_nvfp4` (+ top-k
  роутера последним блоком), `dec_attn_prep` (нормы голов + RoPE + запись
  K/V). Строка живёт в регистрах (4 элемента на нить), квант-эпилоги —
  четвёрка/восьмёрка нитей на группу; e4m3-кодирование битами вместо
  `log2f/exp2f` (результат тот же).
* `best_cu/gemv/gemv_nvfp4.cu` — split-K тайл 16 строк × 8 варпов
  (`mma_gemv_tile_splitk`), групповой запуск до трёх весов (+ строки роутера
  f32 хвостом грида), индексный запуск по таблице экспертов с эпилогом
  `acc[m] += w_p·y` атомиками (аккумулятор обнуляет блок top-k).
* `best_cu/gemv/gemv_mxfp8.cu` — групповой вариант (q/k/v одним запуском).
* `cu/fused/attention/flash_decode_gqa.cu` — блок = (KV-голова, сегмент
  ключей), варп на ключ, головы группы в регистрах; merge с bf16 и/или
  MXFP8-выходом. Инстанциации: голова 256 (nrep 1/2/4/8) и 512 (2/4/8).
* `DecoderModel::forward_block_fused` — сборка слоя: 14 ядер вместо ~74.
  Путь включается `fused_block_ok`: BF16-счёт, полное внимание с
  квант-проекциями одного формата (MXFP8|NVFP4), плотный MLP NVFP4 с
  gelu_tanh, BF16-KV, у MoE — `fused_ready`. Qwen/Muse (silu, F16) не
  трогает. `SYN_FUSED_DECODE=0` — откат на прежнюю цепочку,
  `SYN_QLINEAR_BF16=0` — обход через F16 в QLinear.

**Нумерика.** Слитые ядра повторяют округления host-пути (выход нормы, сумма
с residual, gelu·up — в bf16 в тех же точках), квант-эпилоги — копии
`nvfp4_quant.cu`/`mxfp8_quant.cu`; отличия — порядок редукций, f32-сумма
экспертов вместо f16 и f32-внимание. Сверка шага host/dev: cos 0.9979
(было 0.9977), argmax совпал. Обход BF16→F16 в QLinear, который убрал шаг
B, сам сдвигал логиты: у Gemma тяжёлые активации, и f16 терял младшие
разряды; из-за этого greedy-цепочка на бенч-промпте расходится с прежней
на первой же ничьей — тексты связные, иголка на 3209 токенах находится.
Критерий `graph_step` заменён на взаимный top-5 (argmax при ничьей в
0.1 логита не показателен).

**Профиль после (на токен, nsys; снят на 206 ток/с, до ускорения top-k):**

| ядро | запусков | мкс | ГБ/с |
| :---- | ----: | ----: | ----: |
| эксперты gate/up + down (индексный split-K) | 60 | 1070 | 750 |
| q/k/v MXFP8 групповой | 30 | 927 | 810 |
| `o_proj` MXFP8 | 30 | 525 | 700 |
| плотный gate\|up (+роутер) и down, NVFP4 split-K | 60 | 511 | 710 |
| голова NVFP4 persistent | 1 | 488 | 850 |
| хвосты слоя (`attn_tail` + `ffn_tail`) | 60 | 325 | — |
| geglu+квант (+top-k) | 60 | 250 | — |
| flash GQA split + merge | 60 | 194 | — |
| подготовка внимания | 30 | 62 | — |

**Профиль по умолчанию (`optimal_profile`) для Gemma-4 теперь BF16.** До
09.09 фасад synthos гонял Gemma-4 в F16-счёте с MXFP8-эмбеддингами и
MXFP8-головой — и слитый путь (он собран под BF16, как считает Gemma HF) в
приложении не включался: замер фасада давал 118 ток/с при 210 на бенче. У
профиля сменились три поля: `compute = BF16` (`PrecisionConfig::validate`
раньше отвергал квант с не-F16 счётом — снято, BF16 квант-ядра умеют),
`embed_storage = BF16` (MXFP8-таблица ходит своим ядром и закрывает захват
графа; +0.7 ГБ VRAM), `lm_head_storage = NVFP4` (MXFP8-голова стоила 0.4 мс
из 4.75 на токен, текст чист при обеих). Фасад: промпт 37 токенов → 200
токенов за 1.08 с — **186 ток/с вместе с префиллом** (~192 чистого декода).
KV политика MXFP8 у Gemma не применяется ни к одному слою, и слитый путь
смотрит на dtype кэша самого слоя, а не на политику.

**Что осталось и как мерить дальше.** GEMV читают на 700–810 ГБ/с из ~900
(эксперты — 750: тайлы по 16 строк на 8 варпов, конфигурация `SYN_GEMV_MT`
на скорость не влияет). Хвосты и geglu — латентные цепочки по 5–7 мкс
(`ncu --graph-profiling node` под sudo: один блок, «No Eligible» 70–95 %).
Кандидаты: три блока на `attn_tail` (по выходу на блок), merge внимания
внутрь split-ядра (ещё −25 узлов), софткап головы в эпилог persistent-GEMV,
роутер в bf16 (−27 мкс, но другая нумерика top-k). Профиль снимать так:

```sh
BIN=$(ls -t target/release/deps/gemma4_decode_bench-* | grep -v '\.d$' | head -1)
SYN_GEMMA4_BUNDLE=… SYN_BENCH_TOKENS=32 nsys profile --cuda-graph-trace=node \
  -t cuda -o prof -f true $BIN --nocapture --test-threads=1 decode_cuda_graph
nsys export --type sqlite -o prof.sqlite -f true prof.nsys-rep
sqlite3 prof.sqlite "select s.value, count(*)/30, sum(end-start)/1e3/30 \
  from CUPTI_ACTIVITY_KIND_KERNEL k join StringIds s on s.id=k.shortName \
  where graphId=(select graphId from CUPTI_ACTIVITY_KIND_KERNEL \
  where graphId is not null group by graphId order by count(*) desc limit 1) \
  group by s.value order by 3 desc"
```

(делитель — число повторов графа; memset-узлы — в
`CUPTI_ACTIVITY_KIND_MEMSET` по `graphNodeId`).

## Память карты: почему пришлось трогать MoE

Первый прогон длинного промпта падал с OOM при 21 ГБ живого из 24. Причина —
перемешанная копия NVFP4-веса: её строит ПЕРВОЕ умножение и кладёт в
default-пул, освобождая исходную в weights-пуле. У резидентной MoE за один
префилл задействованы все 3840 экспертов, то есть 12.85 ГБ переезжают из пула
в пул; оба пула держат страницы зарезервированными, и карта кончается при
неизменном живом объёме. Теперь `MoeFfn::load` перепаковывает резидентные
NVFP4-веса сразу, под `WeightsAllocGuard` — копия рождается там же, где
исходная. Побочный выигрыш: батчевый GEMV экспертов не ждёт первого
умножения.

Остальное про пулы — `vram_pools_long_context_2026.md`.

## Кольцевой KV на sliding-слоях

Условие `ring_kv_ok` требовало голову 128 — упиралось в оконное device-ядро.
С инстанциациями на 256 (см. выше) кольцевой буфер включён и для Gemma-4, и
для Gemma-3: sliding-слои держат `окно + RING_SLACK` вместо всего контекста,
и ставка падает с **225 до 20 КБ на токен**. На 128k контекста это 2.6 ГБ
вместо 29 — разница между «влезает» и «не влезает».

Кольцо не включается там, где последовательность считается ОДНИМ куском:
энкодерный проход (`forward_hidden_states`, текст-кондишен LTX) зовёт
`make_kv_cache_full(..., allow_ring = false)`. Иначе промпт длиннее
`окно + RING_SLACK` падал бы с «chunk не помещается» — в чанках его там
никто не режет.

## Вызовы инструментов: протокол хода и парсер (09.09)

Симптом в чате MyLife: на «прочитай полностью все заметки» модель писала
`call:notes{action:read,page:all}` обычным текстом, инструмент не вызывался,
а следующим ходом она «пересказывала» выдуманное содержимое.

Причина — протокол хода Gemma-4 целиком на спецтокенах, которых в
декодированном тексте нет (`LlmTokenizer::decode` идёт со
`skip_special_tokens`):

```text
<|turn>system
<|tool>declaration:notes{description:<|"|>…<|"|>,parameters:{…}}<tool|><turn|>
<|turn>model
<|channel>thought
размышления<channel|>
<|tool_call>call:notes{action:<|"|>read<|"|>,page:<|"|>all<|"|>}<tool_call|><|tool_response>
```

`<|tool_call>`/`<tool_call|>` (48/49), кавычка строки `<|"|>` (52),
`<|channel>`/`<channel|>` (100/101) — отдельные токены. ChatML-парсер
synthos ищет `<tool_call>` буквами и ничего не находил; кавычки пропадали
вместе с маркерами — отсюда `action:read` без кавычек в ленте. Ход
завершают `<turn|>` (106) и `<|tool_response>` (50) — оба в
`generation_config.json`, фасад берёт eos оттуда.

Аргументы — не JSON, а нотация шаблона: ключи без кавычек, строки в
`<|"|>…<|"|>`, вложенные `{}`/`[]`, числа/логические/`null` как есть;
ключи отсортированы (`dictsort`), так модель их и пишет.

**Что сделано.**

* `synaptix-tokenizer/src/parsers/gemma4.rs` — разбор по id токенов:
  `Gemma4Ids::detect` (маркеры кодируются одним токеном), `Gemma4StreamParser`
  раскладывает дельты на ответ / размышления (первая строка после
  `<|channel>` — имя канала, отбрасывается) / тело вызова, `parse_call`
  переводит нотацию в JSON-объект. Кавычка-токен хранится сентинелом
  `U+E000`. Незакрытое тело на конце потока разбирается тоже.
* synthos: третий вариант `StreamParser::Gemma`, стопы — только `eos_ids`
  бандла (`<|im_end|>` в словаре нет), промпт хода с поправкой
  `prompt_for_model`. История с вызовами идёт в шаблон структурно
  (`tool_calls` + `role=tool` с `name`) — шаблон сам рендерит
  `<|tool_call>call:…` и `<|tool_response>response:имя{value:…}`; сквозной
  рендер проверяет тест `gemma4_template_round_trip` (ignored, нужен бандл).
* **Пустой канал размышлений.** При `enable_thinking` шаблон продолжает
  ход после результата инструмента с `<|channel>thought⏎`; если модель не
  думала, она сразу пишет `<channel|>`, а при следующем рендере шаблон
  пустые размышления опускает — промпт расходится с прошлым, и префикс-KV
  (он живёт только концом прошлого промпта) терял весь контекст: в прогоне
  22 с префилла на 11k ток. `gemma4_restore_empty_thinking` возвращает
  `<|channel>thought⏎<channel|>` после каждого `<tool_response|>`, за
  которым идёт не размышление и не конец промпта.

**Живой прогон** (`agent_smoke`, tools=bash,notes, thinking включён):
`bash` → «В текущем каталоге 13 файлов.»; `notes read pages=[all]` —
аргументы с массивом разобраны, 24 страницы прочитаны, пересказ с
размышлениями. Что осталось: между сообщениями пользователя размышления
прошлых ходов шаблон вырезает (`thinking_gate`), так что с включёнными
размышлениями каждое новое сообщение префиллит контекст заново — это
свойство шаблона, как и у Qwen3.x; и сам префилл был медленным (23k ток. за
132 с при 3.4 ГБ свободной VRAM) — отдельный вопрос к чанкам префилла под
давлением памяти.

## Префилл: 845 → 10 000 ток/с (10.09)

Замер — `crates/synaptix/tests/gemma4_prefill_bench.rs` (промпт из
повторяющихся абзацев, `SYN_BENCH_PROMPT` токенов, `SYN_BENCH_CHUNKS` —
размеры чанка через запятую, `0` — как приложение; `SYN_PREFILL_PROF=1` +
`SYN_MOE_PROFILE=1` — разбивка по стадиям):

```sh
SYN_GEMMA4_BUNDLE=~/Storage/syn_models/gemma-4-26b-a4b-it.syn \
SYN_BENCH_PROMPT=4096 SYN_BENCH_CHUNKS=0 \
  cargo test -p synaptix --release --test gemma4_prefill_bench -- --nocapture --test-threads=1
```

Стартовая точка на 4172 токенах — 4.36 с (957 ток/с), в приложении на 23k
было 132 с. Разбор по стадиям (`SYN_PREFILL_PROF`) и по ядрам (nsys) дал
три причины, каждая — не там, где ожидалось:

| шаг | что было | что сделано | 4172 ток. |
| :---- | :---- | :---- | ----: |
| — | старт | | 4359 мс |
| 1 | 25 sliding-слоёв (голова 256, окно 1024) не проходили ни в одно flash-ядро и падали в SDPA: `repeat_kv` плюс матрица скоров nh×s×att_len в F32 — 35 мс на слой | оконное device-ядро `flash_splitq_*_win_dev` общее по числу запросов (сетка по q-тайлам, causal и окно внутри) — на префилле оно и зовётся | 3012 |
| 2 | 5 global-слоёв с головой **512** шли через `flash_decode_split` (decode-ядро, один запрос на блок) — 93 мс на слой, 62 % всего времени | новое ядро `flash_splitq_*_hd512`: Q-тайл 64×512 в smem, S по всем 512, O — половиной головы на блок (grid.z = 2, S пересчитывается дважды, 1.5× FLOP); smem 90 КБ при лимите 99 на блок у sm_120 (BN = 16). 2.2 мс на слой при 2048 запросах | 1237 |
| 3 | MoE: на каждого из 128 экспертов ~13 ядер (срез, обнуление хвоста, квант, GEMM, два среза gate/up, gelu, mul, обнуление, квант, GEMM, каст), GEMM по 22 блока на 170 SM | строки эксперта — в сегменте, выровненном на 128 (тайл масштабов NVFP4); один квант всего буфера; **групповой GEMM** `nvfp4_mma_gemm_shuf_2dr_…_grouped` — один запуск на все эксперты слоя с таблицей адресов (`QuantWeight::gemm_grouped`); слитый `gelu_tanh(gate)·up` + квант (параметр `act` у `silu_mul_quantize_nvfp4_fast`); выход GEMM сразу в BF16 | 497 |
| 4 | взвешивание, обратная перестановка и сумма по слотам — три ядра по всему буферу | `moe_combine`: `out[t] = Σ_s w·y[inv]` одним ядром; полный тайл в оконном flash без масок, если тайл целиком внутри окна | **414** |

Итог: **414 мс, 10 100 ток/с** на 4172; 16 872 ток. — 2.29 с (7 400 ток/с),
24 504 ток. — 3.33 с (7 350 ток/с) при 3.7 ГБ свободной VRAM. Первый токен
и ответы smoke-тестов (иголка за окном, шаблон) не изменились; графовый
декод — 212 ток/с, как был.

**Чанк префилла.** Кольцевой KV sliding-слоёв (`w + RING_SLACK`) не
принимает чанк длиннее `RING_SLACK` = 2048 — `DecoderModel::max_prefill_chunk`
теперь режет любой запрошенный чанк (и «весь промпт» из фасада) до него, а
графовый `generate_with_graph_resume` берёт 2048 вместо 256: цена слоя MoE
почти не зависит от числа токенов в чанке, и 256 давало восьмикратный
паддинг сегментов. Чанк самой MoE (`MoeConfig::chunk`) у Gemma-4 — 2048
(`SYN_MOE_CHUNK` для опытов); пик активаций на чанк — сбор строк
`(T·k + 128·E)·H` в BF16 плюс выход gate_up, ~0.3 ГБ.

**Что осталось (nsys на 4172 ток.):** групповые GEMM 98 мс (≈290 TFLOPS,
дальше — только паддинг сегментов: при 2048 токенах до 40 % строк —
хвосты), сбор строк 32 мс, оконный flash 55 мс (62 TFLOPS), flash HD=512
44 мс (70 TFLOPS, один блок на SM из-за smem), проекции внимания MXFP8 47 мс,
нормы 28 мс, роутер в F32 16 мс. Кандидаты: сегменты по 64 строки (нужен
свой тайл масштабов), двухстадийный конвейер в ядре HD=512, роутер в BF16.

`SYN_MOE_SEGMENTED=0` возвращает прежний поэкспертный цикл (для сверки).

## Чего нет

* **аудио.** У 26B A4B его нет и в оригинале (только E2B/E4B/12B), но код
  башни звука не написан — если появится другая Gemma-4, её придётся делать;
* **PLE и общий KV между слоями.** `hidden_size_per_layer_input > 0`
  (раскладка E2B/E4B) и `num_kv_shared_layers > 0` конфиг отвергает явной
  ошибкой, а не считает неправильно;
* **видео.** Кадры сводятся к тем же мягким токенам, но разметка промпта с
  таймкодами не сделана;
* **оффлоад блоков.** Блок с MoE-веткой на хост не переносится
  (`block_offload_shape` для Gemma-4 отвечает `None`);
* **спекулятивный декод.** Ни MTP-головы, ни драфтера у модели нет.
