# Агент Syn-чата ↔ нодовые пайплайны (2026-08-20)

Агент чата получил полный доступ к нодовому редактору: находит пайплайн
(встроенный или кастомный шаблон), сочиняет сценарий, заполняет ноды
(промпты, параметры, ref-входы из вложений чата), проверяет VRAM/RAM, при
нехватке VRAM выгружает сам себя на время прогона, запускает граф, показывает
живой статус и отдаёт результаты (видео/аудио) прямо в чат.

## Два новых инструмента

### `system` (`agent/tools/system.rs`)

- `action=status` — VRAM всего / свободно по драйверу / доступно (свободно +
  слабина пула активаций — по ней принимаются решения о памяти), RAM,
  нодовые модели из `crate::models` (с id) и состояние чат-LLM.
- `action=unload` — выгрузка нодовых моделей (`id` из status или `all=true`)
  + `trim_all`. Чат-LLM отсюда НЕ выгружается: worker хода держит
  `Arc<LoadedSynModel>` — веса не освободятся. Для неё `free_vram` у run.

### `pipelines` (`agent/tools/pipelines.rs`)

Работает со СЛУЖЕБНОЙ вкладкой редактора: одна на чат, скрытая из полосы
вкладок (`OpenTab.agent_chat`/`hidden`, `EditorWorkspace::ensure_agent_tab`),
раскрывается ссылкой «Открыть граф» из чата (`reveal` + роут `nodes`).

| action | Что делает |
|---|---|
| `list` | шаблоны (builtin + custom), вложения чата, состояние вкладки |
| `nodes` | схемы видов нод из `REGISTRY`: порты, поля, пример state-JSON (снят с `default_runtime` → `runtime_to_state`); без `filter` — компакт-список |
| `open` | загрузить шаблон в служебную вкладку (`load_into_ctx`) |
| `graph` | снимок графа (ноды + state + связи), state клипуется до 700 симв. |
| `apply` | `graph` (Template-JSON, mode=replace/merge; id/pos автозаполняются), `set_state=[{node,state}]` (вариант state сверяется с kind — mismatch это ошибка, а не молчаливый no-op), `connect`/`disconnect` (резолв портов по registry, самосвязи/дубли отбрасываются) |
| `save_template` | граф вкладки → кастомный шаблон (`templates::create` + `bump_revision`) |
| `run` | прогон — см. ниже |

Строки `attachment:<имя|sha-префикс|last>` в payload'е apply резолвятся в
путь blob'а вложения текущего чата через `blobs::model_path` (derived-PNG
для GIF/HEIC и т.п. — формат, читаемый `synaptix-io`).

## Прогон (`pipelines action=run`)

`run` перехватывается agent-loop'ом ДО `tools::execute`
(`pipeline_run::parse_run_call` в `session.rs`) — он завязан на жизненный
цикл LLM. Subagent'ам run недоступен (явная ошибка в `pipelines.rs`).

Последовательность (`session::run_pipeline_tool` + `syn_chat/pipeline_run.rs`):

1. **prepare** (main thread, ДО выгрузки LLM): в графе есть enabled-ноды с
   `on_run`; пустые/относительные пути save-нод (`LtxVideoSave`,
   `H3VideoSave`, `SaveToFile`) автозаполняются в
   `~/.local/share/synthos/outputs/<chat_id>/<run_id>/node<N>.<ext>`;
   снимается (len, mtime) существующих файлов — отличать свежую запись.
2. **free_vram=true**: `*kv_slot = None` СВОИМ guard'ом (иначе
   `drop_kv_session` из `unload()` отложил бы дроп до конца хода) → дроп
   последней `Arc` хода (upfront-клон `model_for_compact` убран — пост-
   ходовой автокомпакт берёт модель из реестра заново) →
   `SynModelRegistry::unload()` → `reclaim_vram`. Ограничение: media-
   эмбеддинги текущего хода (`Vec<MediaEmbedding>`) не освобождаются.
3. **start**: `run_controls::start_run(ctx, Some(oneshot))`. Итог
   (`RunOutcome`) стреляет в трёх местах: очередь опустела, Stop/отмена,
   замещение новым Run. Синхронно упавшие ноды (hook вышел, не тронув
   `running` — например sampler без входа) дренируются `advance()`-циклом
   и не вешают очередь.
4. **wait**: `tokio::select!` c `wait_abort`; abort хода →
   `cancel_active_run()` — сброс очереди + взвод cancel-флагов активных нод
   (`NodeRuntime::run_cancel_flag`; ACE-Step Generate флага не имеет и
   досчитывает).
5. **артефакты**: файлы save-нод, появившиеся/изменившиеся за прогон →
   `attach::ingest` (CAS + thumbnail) → вложения tool-result сообщения
   (`push_tool_result_with`). В промпт не утекают (`build_history` отдаёт
   ToolResult без attachments; vision-башня не поднимается), в ленте —
   плитки + полноэкранный `media_viewer`; при `tool_display_mode=hidden`
   медиа всё равно показывается.
6. **reload**: `model_registry::load_with_notify(path, policy, tx)` —
   worker ждёт oneshot. Ошибка reload'а → внятная ошибка хода ПОСЛЕ пуша
   результатов. Следующий ход — полный префилл (prefix-KV сброшен,
   `KERNEL_CACHES_WARM` сброшен — штатно).

Ошибки нод собираются в итог через новый generic-хук
`NodeRuntime::run_error_signal` (watcher их не видит — downstream упавшей
ноды всё равно стреляет, поэтому «успех» прогона определяется по отчётам).

## Живой статус в чате

`message_bubble::pipeline_live_card` — под последним tool-call `pipelines`,
пока `run_state == Running`: «нод N/M · <активные ноды с %> · elapsed»,
кнопка отмены (= abort хода) и «Открыть граф». Прогресс — из
`NodeRuntime::run_progress_signal` через `run_controls::active_nodes_status`
(подписка внутри Reactive). Свой `timing::ticker` — бейдж нодовой страницы
в чате не смонтирован. Известные дыры прогресса: ACE-Step Generate не пишет
`progress_pct` вовсе, Lipdub пишет вехи — карточка показывает только имя.

## Guard повторов и промпт

- Повторный запуск того же графа — новое значение `run_id` в аргументах
  (иначе guard consecutive-повторов срежет вызов).
- Правила пайплайнов добавляются в system prompt только при активном
  инструменте `pipelines` (текст зависит лишь от набора инструментов —
  префикс-KV стабилен).

## Проверка

- `cargo test --lib` — юниты: схема нод/Template-JSON (`tools::pipelines`),
  parse_run_call/envelope (`syn_chat::pipeline_run`), service-вкладки
  (`node_editor::persist`), промпт (`system_prompt`).
- E2E: чат с Qwen3.8-27B → «сгенерируй 5-сек видео заката» → system status
  → open builtin-ltx-text-to-video → apply (промпт) → run(free_vram=true)
  → живая карточка → mp4 в чате → LLM перезагружена. Лёгкий путь: ACE-Step
  без free_vram.

## Разбор первого боевого прогона (2026-08-20)

Чат с Qwen3.8-27B попросили сгенерировать 5-секундное видео. Агент дошёл до
`run` и получил «action=run доступен только основному агенту чата (не
subagent)», хотя субагентов в сессии не было. Разбор дал четыре независимых
дефекта — все починены:

1. **`run` не перехватывался.** Модель обрамляет значения аргументов
   переводами строк (`{"action":"\nrun\n"}`). `parse_run_call` сравнивал
   значение как есть, вызов не опознавался как прогон и уходил в
   `tools::execute` — а тот нормализует аргументы (`normalize_args`), и уже
   `"run"` попадал в subagent-ветку `pipelines.rs`. Теперь `parse_run_call`
   нормализует аргументы тем же нормализатором.
2. **`set_state` требовал числовой id.** Снимок графа печатает
   `[2] h3_checkpoint`, модель писала `"node": "h3_checkpoint"` и получала
   «нужно поле node (id ноды)» — поле было на месте. `resolve_node_ref`
   принимает число, строку с числом и slug вида ноды (пока такая нода в
   графе одна); то же для `connect`/`disconnect`.
3. **Модели вне основного каталога были невидимы.** Инвентарь `list` знал
   только `models_dir`, а LTX и Gemma лежали в кэше HF-загрузок — агент
   доложил «LTX-моделей в каталоге нет» и ушёл на H3. Теперь инвентарь
   печатает оба каталога (основной + кэш HF), а LTX перепакован в `.syn` в
   основной (см. `ltx_syn_bundle_2026.md`).
4. **`*_idx`-поля были непрозрачны.** В state попадает голое число, и выбор
   кванта/устройства/аспекта был случайным. `action=nodes` печатает под
   примером state расшифровку: `quant_dit_idx: 0=nvfp4, 1=mxfp8, 2=dense
   (compute)` и т.д. (таблица `enum_hints` зеркалит `*_OPTIONS` нод).

Побочно: компакт-список нод подсказывает, что `filter` — подстрока (`h3`,
`ltx` отдают всё семейство за один вызов), иначе агент тратит по ходу на
каждую ноду.

### Второй прогон: фильтр `nodes` (там же)

С починенным инвентарём агент увидел LTX-бандлы и открыл `builtin-ltx-text-to-video`,
но встал на `nodes`: `filter` матчился как ОДНА подстрока, а модель писала туда
список нужных нод вместе с именами полей («ltx_checkpoint ltx_text_encoder
quant_dit_idx …»). Совпадений нет → ошибка без данных → модель меняла строку
и звала снова: 16 вызовов подряд, пока guard повторов не поймал дословный дубль.

Теперь `filter` — набор токенов (пробел/запятая/точка с запятой), матч по
любому: перечисление нод возвращает их все. Промах фильтра больше не ошибка —
возвращается компакт-список видов нод, то есть ровно то, ради чего инструмент
и звали. Общее правило для агентских инструментов: **пустой результат должен
нести данные для следующего шага**, иначе модель уходит в перебор.

### Третий прогон: `list` не влезал в лимит истории

`pipelines list` вырос до ~11.8 тыс. символов (описания шаблонов до 600
символов + инвентарь двух каталогов + полный снимок графа со state). Лимит
результата инструмента в истории хода тогда был статическим —
`HISTORY_TOOL_RESULT_CHARS` = 8000 символов (с 07.09.2026 — укладка в остаток
окна по токенам, `budget::fit`), и клип резал СЕРЕДИНУ: агенту доставались шаблоны и хвост снимка
графа, а раздел «Модели в каталоге» пропадал целиком. Он повторял `list`
(ловил guard повторов) и уходил искать `.syn` через `bash find`.

Ужат сам вывод, а не лимит:

- описания шаблонов клипаются до 90 символов (`clip_desc`);
- инвентарь печатает имена относительно каталога, полный путь — в шапке
  раздела (`пути: <каталог>/<имя>`);
- служебная вкладка — сводкой `graph_brief` (ноды без state, связи числом);
  полный снимок остаётся за `action=graph`.

Итого ~7 тыс. символов вместо 11.8 тыс. Тест
`templates_section_fits_history_budget` держит раздел шаблонов < 4500
символов, чтобы новые builtin-шаблоны не вернули регрессию.

### Четвёртый прогон: `apply` и JSON-в-строке

Маршрут дошёл до `apply`, и там встал: модель передала `set_state` **строкой**
с JSON внутри (`"set_state": "[{\"node\": 13, …}]"`). `as_array()` дал `None`,
блок пропустился, и вызов упёрся в «apply без изменений: передай graph,
set_state, connect или disconnect» — ошибку, отрицающую то, что агент видит в
собственном вызове. Дальше `{"action":"apply"}` → `{}` → guard повторов.

Инструмент стал терпимее к тому, как модели сериализуют аргументы:

- `set_state`/`connect`/`disconnect`/`graph`/`state` принимают структуру,
  строку с JSON и одиночный объект вместо массива (`coerce_array`,
  `unwrap_json_string`);
- битый JSON внутри строки объясняется с позицией разбора, а не прячется за
  общим «apply без изменений»;
- «apply без изменений» перечисляет пришедшие ключи и их типы плюс шаблон
  правильного `set_state`;
- `free_vram` у `run` и `all`/`id` у `system` тоже читаются из строк.

Отдельно: `apply` больше не откатывает весь вызов из-за одного плохого
элемента. Валидные `set_state`/`connect` применяются, проблемные собираются в
раздел «⚠ не применено» — агент видит прогресс и чинит остаток, а не
пересобирает вызов целиком.

Ещё в этом прогоне подтвердились прошлые фиксы: `list` доехал целиком с
разделом моделей, промах фильтра `nodes` вернул каталог слагов и агент попал
со второй попытки, пути LTX подставлены верные (`ltx-2.3-22b-dev.syn`,
`ltx-gemma-3-12b-qat.syn`, upscaler) с `quant_dit_idx: 0` = nvfp4.

Профилактика на следующий шаг: `prepare` проверяет `upscaler_path`, когда в
графе есть включённая `LtxUpscale` — иначе граф падал бы уже после выгрузки
LLM и загрузки 46-гигабайтного DiT.

### Пятый прогон: девять ходов и текст вместо `run`

`apply` наконец применился (state четырёх нод), но прогон так и не стартовал.
Девять вызовов вместо шести: два ушли на `set_state` строкой с битым JSON
(модель ставит запятую вместо двоеточия и повторяет ошибку), два — на пустой
`{"action":"apply"}`, один съел guard повторов. После guard'а модель выдала
текст «Запускаю прогон…» **без вызова** `run` — ход закончился, и запуска не
случилось.

Правки бьют в оба источника потерь:

- пустой `apply` больше не ошибка: возвращается сводка графа и прямая фраза
  «если граф уже собран — следующий шаг action=run» (отказ загонял в повтор);
- успешный `apply` отвечает сводкой вместо полного снимка со state (~2.5 тыс.
  символов на вызов) и называет следующий шаг;
- `open` сразу перечисляет незаполненные пути моделей (`missing_model_paths`
  по тому же правилу, что и pre-check прогона) — агент узнаёт, что заполнять,
  на шаг раньше;
- ошибка разбора JSON-строки печатает фрагмент вокруг позиции сбоя
  (`около: …`), чтобы починка была прицельной, а не наугад;
- в промпт добавлено: объявил действие — выполни его в этом же ходу,
  текстовый ответ завершает ход.

### Шестой прогон: генерация прошла, результат — в ленте

Маршрут отработал целиком за шесть вызовов (list → status → open → nodes →
apply → run), прогон занял 2м14с, mp4 приложился к сообщению. Всплыли две
вещи.

**Вокодер не читал `.syn`.** `LTX Audio Decode` падал с `vocoder: load:
safetensors: header too large`: `BaseVocoder::load`/`VocoderWithBwe::load`
открывали путь через `SafetensorsLoader::open` напрямую, мимо
`loader::open_weights` — единственное место в LTX, пропущенное при переводе
на бандлы. Видео вышло без звука. Исправлено, оба пути идут через общий
хелпер.

**Результат смотрели только через модальное окно.** Ноды-просмотрщики
(Видео-плеер, Аудио-плеер) держат результат в памяти, и в чат он не попадал
вовсе — приходил лишь файл save-ноды, плиткой-превью. Теперь:

- `collect_viewer_outputs` материализует то, что показывает просмотрщик
  (кадры → mp4 через общий `video_save::encode_mp4`, буфер → wav), и
  прикладывает к сообщению. Дубли не плодим: если save-нода уже отдала видео
  или аудио, соответствующий просмотрщик пропускается;
- `media_inline` рисует в пузыре настоящий плеер — видео с постером и ⏵
  (декодер поднимается только по клику), аудио с волной и play/pause,
  картинку во всю ширину карточки;
- у каждого вложения есть «Сохранить как…» (копия blob'а из CAS) и «Открыть
  внешним приложением»; та же кнопка добавлена в полноэкранный просмотрщик;
- декод и воспроизведение аудио вынесены в общий `media_audio` — лента и
  просмотрщик больше не держат по своей копии этой механики.

### Седьмой прогон: три «Продолжить» и плеер, который держал ход

Ход обрывался трижды, и пользователь каждый раз жал «Продолжить». В логе —
`tool_parser: stream закончился внутри <tool_call> без </tool_call> —
отбрасываем`, причём в одном случае с целым телом:
`{"name":"pipelines","arguments":{"action":"run","free_vram":true,...}}`.
Модель закончила генерацию сразу после JSON, не написав закрывающий тег, а
парсер выбрасывал такой вызов целиком: `tool_calls=0`, цикл завершался без
действия. Теперь `finish()` пробует разобрать накопленное тело и принимает
вызов, если JSON целый; выбрасывается только то, что оборвалось на полуслове.

Второе: прогон висел на ноде «Видео-плеер» (8/9, 1:30 на скриншоте, «1м 1с»
в прошлом отчёте) — её `busy_signal` возвращал `is_playing`, и секвенсер
ждал, пока ролик доиграет. Всё это время агентский ход стоял с выгруженной
LLM, а пользователю оставалось нажать «Отменить». Плеер показывает результат,
а не считает его: `busy_signal` теперь `None`, воспроизведение продолжается
само, downstream-нод у плеера нет.

### Восьмой прогон: медиа в ленте, OOM после возврата LLM

Карточка-плеер появилась, но всплыло три вещи.

**Медиа жило внутри карточки инструмента.** Вложения висели на tool-результате
и сворачивались вместе с ним. Теперь `push_tool_result_with` кладёт медиа
отдельным сообщением ленты (`ChatMsg::assistant_empty` + вложения), а
`message_bubble` рисует такое сообщение одним рядом карточек без пустого
пузыря. В историю для модели оно не идёт — лента и история живут отдельно.

**Клик по постеру открывал просмотрщик вместо воспроизведения.** Логика
перевёрнута: клик по кадру запускает инлайн-плеер, полноэкранный просмотр —
отдельной кнопкой в строке действий. Инлайн-плеер поднимается с
`HwAccel::None`: NVDEC держит контекст в той же VRAM, куда возвращается
чат-LLM, и превью ролика не стоит отнятых у модели мегабайт.

**OOM после прогона.** По логу: перед прогоном свободно 22001 МБ, после —
9067 МБ; LLM грузится в остаток (веса 7744 МБ, свободно 1323 МБ), KV-ринг
считает «влезает 0 ток», первый forward падает с `alloc_zeros(3145728) after
trim+retries: OOM`. Нодовые модели прогона держали ~13 ГБ. Перед возвратом
LLM теперь делается `models::unload_all()` + `trim_all()` с логом «VRAM
свободно X -> Y MB».

### Девятый прогон (2026-09-11): `free_vram` не выгружал модель

Чат «TestMusic», «сгенерируй русский рэп о любви», дважды — на
qwen3.8-flash-next и на Gemma-4 26B. Оба раза OOM, хотя `free_vram=true`.
В журнале выгрузки перед прогоном:
`выгрузка модели: ссылок было 4 … VRAM свободно 2666 -> 3786 MB` и
`LLM выгружена (+0 MB …)`. Ссылок должно быть две (реестр и локальный `held`
в `unload()`), значит, веса пережили выгрузку:

- flash-next: ACE-Step LM 4b (8.4 ГБ) упал на 14-м слое —
  `alloc H2D(5242880): CUDA_ERROR_OUT_OF_MEMORY`; следом не поднялась и
  сама LLM (свободно 3786 МБ);
- Gemma-4: default-пул 14080/14039 МБ после «выгрузки», перезагрузка
  упала с `[OOM_TOP] 2230272 B × 4808 = 10.72GB` — это эксперты старой
  копии той же модели.

Две лишние ссылки — счётчики токенов из `tools::budget::model_counter`
(появились 07–08.09, dfba00b/0082f05): замыкание клонировало
`Arc<LoadedSynModel>`, а живёт оно весь ход — в статическом `SLOT`
бюджета (guard `_tool_budget` охватывает цикл вызовов, внутри которого и
идёт `run_pipeline_tool`) и в `MediaCaps.doc_budget`. Отпускались только
по окончании хода — поэтому сразу после ошибки ручная загрузка модели
проходила.

Исправлено: `LoadedSynModel.tokenizer` — `Arc<LlmTokenizer>`, счётчик
держит только токенизатор (RAM). `run_pipeline_tool` проверяет выгрузку
через `Weak` и пишет `LLM НЕ освобождена — живых ссылок N`, если кто-то
снова придержит модель.

Попутно: агент записал в чекпойнт ACE-Step голые имена бандлов
(`"lm_path": "acestep_5hz_lm_4b.syn"` — ровно так их печатает схема ноды),
а `resolve_paths` брал override как есть, от cwd процесса: «lm bundle не
найден». Относительный override теперь резолвится от `models_dir`.

## Известные ограничения

- Прогон в subagent'е запрещён; статус-поллинг не нужен (run блокирующий).
- `system unload` не ждёт занятых воркеров (честно сообщает «удерживается»).
- Отмена не останавливает ACE-Step Generate (нет hooks в `generate_music`).
- Порты при `connect` резолвятся по имени, но типы PortKind не
  валидируются (как и в UI) — несоответствие всплывёт на evaluate.
