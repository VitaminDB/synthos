# synthos — RAG / Knowledge Base (2026)

## Что это

Подсистема Retrieval-Augmented Generation для AI-агента synthos. Пользователь
создаёт **коллекции документов** (локальные файлы, папки, PDF, URL),
которые индексируются эмбеддером и FTS5 локально (без облака), а модель
получает к ним доступ через **tool `kb_search`** или (опционально)
auto-augment system prompt.

Никаких внешних сервисов — всё считается локально. Embedding-модель
работает на synaptix (CPU/CUDA/Metal), хранилище — `rusqlite` (bundled,
без системного sqlite). Таким образом, RAG — это нативное
расширение, не требующее запуска отдельных процессов помимо уже
работающего `llama-server` для chat-модели.

## Архитектура

```
┌──────────────────────────────────────────────────────────────┐
│ Settings → Базы знаний (pages/settings/knowledge_base)       │
│   ↕ KbCtx (signals: registry, active_*, ingest_progress…)    │
├──────────────────────────────────────────────────────────────┤
│ Ingest pipeline (kb::ingest, kb::runner)                      │
│   DocSource → parse → chunk → embed → store                  │
├──────────────────────────────────────────────────────────────┤
│ Hybrid search (kb::search) — BM25 ⊕ cosine через RRF          │
│   ↕                                                           │
│ Store (kb::store) — rusqlite + FTS5                          │
└──────────────────────────────────────────────────────────────┘
```

Один файл `~/.config/synthos/kb/<collection_id>.sqlite` = одна
коллекция. Регистрация коллекций — на лету через скан каталога;
в `config.json` ничего про список коллекций не пишется (устойчиво
к ручным удалениям файлов).

## Работа end-to-end

1. **Модели** — `.syn`-бандлы в каталоге из Settings → «AI модели»
   (`AppConfig.models_dir`): `bge-m3.syn` (эмбеддер) и
   `bge-reranker-v2-m3.syn` (реранкер). Приложение находит их само
   (`kb::models`): сначала путь из `KbConfig`, если он существует (или он же
   с `.syn`), затем известные имена в `models_dir`, кэше HuggingFace и
   закладках проводника бандлов, затем любой `.syn` с `arch = xlm-roberta` и
   `purpose = embed` / `reranker`. Устаревший путь в конфиге поиску не мешает.
   Нет бандла — скачать `BAAI/bge-m3` / `BAAI/bge-reranker-v2-m3` и упаковать:
   `syn-pack ~/models/bge-m3 -o <models_dir>/bge-m3.syn`.

2. **Запустить synthos**. Устройство моделей KB — в карточке «Модели»
   (CPU по умолчанию; GPU — F16, ~2 ГБ VRAM на обе модели, кодирование в
   десятки раз быстрее: 3 коротких текста 15 мс против 520 мс).

3. **Settings → Базы знаний**: «+» в правой панели или кнопка на пустой
   странице. Грузить модели руками не нужно: первая индексация, пробный
   поиск, `kb_search` и auto-augment поднимают их сами
   (`loader::embedder_ready`); кнопки «Загрузить / Выгрузить» в карточке
   «Модели» — чтобы прогреть заранее или освободить память.

4. **Добавить источники**: строки «Файлы» / «Папка» / «Веб-страница».
   Pipeline индексирует и пишет прогресс в `KbCtx.ingest_progress`
   (Reactive UI обновляется на каждом шаге).

5. **Привязать к чату**: в правой панели «Использовать в чате» —
   тогглит коллекцию в `active_in_chat_ids`.

6. **В чате**: включить tool `kb_search` (Settings → Общие →
   tool toggle, либо напрямую через UI выбора tools). Модель сама
   позовёт `kb_search` когда нужно — увидите tool-bubble с топ-K
   фрагментами и продолжение ответа с цитированием источника.

## Hybrid search

`kb::search::hybrid_search`:
1. Параллельные top-K кандидаты от BM25 (FTS5) и cosine (BLOB scan).
2. Reciprocal Rank Fusion: `score = Σ 1/(60+rank+1)` по двум источникам.
3. Top-K по итоговому score, поднимаем тексты из БД.

RRF не требует калибровки скоров между источниками; на практике
обходит линейные комбинации с нормализацией.

### Опциональный rerank (cross-encoder)

`kb::search::hybrid_search_with_rerank(store, embedder, reranker, query,
top_k, multiplier)` — расширенная версия с дополнительной фазой
переранжирования через cross-encoder (`synaptix::facade::rerank::Reranker`,
реализация: `BgeReranker` на `BAAI/bge-reranker-v2-m3`).

Идея: RRF быстро отбирает `top_k × multiplier` кандидатов из BM25+cosine,
а тяжёлый, но точный cross-encoder сортирует их в финальные `top_k`.
Прирост качества top-K по MRR — 10–20% на типичных RAG-бенчмарках
(MS MARCO, BEIR), цена — один forward модели ~270M params на пару
`(query, doc)`.

- `multiplier` (`KbConfig.reranker_top_k_multiplier`, default 4) — чем
  больше, тем выше recall, но дороже cross-encoder.
- При сбое реранкера (load fail / inference error) логируется warn и
  возвращается чистый RRF — деградация безболезненная.
- В `SearchHit.rerank_score: Option<f32>` сохраняется итоговый score,
  поле `score` подменяется на rerank-score, RRF-метаданные (`bm25`,
  `cosine`, `bm25_rank`, `cosine_rank`) остаются для отладки.

#### Загрузка

`synaptix::facade::rerank::load_reranker(RerankerConfig)` и
`facade::embedding::load_embedder(EmbedderConfig)` грузят модель на synaptix
(CPU/CUDA, dtype f32/f16/bf16): путь-файл — `.syn`-бандл, путь-каталог —
распакованный HF-снапшот (config.json + tokenizer.json + model.safetensors).

`kb::loader::reranker_ready(kb, plan)` — тот же ленивый путь, что у эмбеддера;
`Ok(None)` при `reranker_enabled=false`. Поиск без реранкера не падает:
`kb_search`, auto-augment и пробный поиск логируют причину и идут по RRF.

#### Конфиг (`KbConfig`)

```toml
reranker_model_path     = ""                             # "" = найти bge-reranker-v2-m3.syn в models_dir
reranker_device         = "cpu"                          # "cuda" | "metal"
reranker_dtype          = "f32"                          # "f16" | "bf16"
reranker_enabled        = true
reranker_top_k_multiplier = 4
reranker_max_tokens     = 512
```

`synaptix`: `cargo test -p synaptix --release --test kb_bundles` (обе модели из
бандлов; `KB_DEVICE=cuda` — на GPU). `synthos`: `tests/kb_bundles_e2e.rs` —
устаревший путь в конфиге → автопоиск → загрузка → индексация → поиск с

## Хранение vector'ов

В `chunks.embedding` BLOB лежит `f32[dim]` little-endian, всегда
L2-нормализованный (cosine = dot product без деления).

### Два режима vector-поиска

Cтратегия выбирается в `kb::vector_index::VectorIndex` на основе
`KbConfig.vector_index_kind` + размера коллекции.

| Режим          | Когда                                  | Что внутри                                                  |
|----------------|----------------------------------------|-------------------------------------------------------------|
| `scan`         | до ~50–100k чанков (или явно)          | full-scan по `chunks.embedding` + cosine в Rust (`<50ms`).  |
| `sqlite-vec`   | от `vector_index_threshold` чанков     | KNN над `chunks_vec` (vec0 virtual table из crate `sqlite-vec`). |
| `auto` *(default)* | выбирается по `chunk_count` за порог | `sqlite-vec`, если он зарегистрирован и порог пройден; иначе `scan`. |

`chunks_vec` — это `VIRTUAL TABLE USING vec0(chunk_id INTEGER PRIMARY KEY,
embedding FLOAT[<dim>])`. `chunk_id` совпадает с `chunks.id`, embedding
хранится тем же `f32[N]` LE BLOB'ом, что уже лежит в `chunks` —
дублирование на диске, но никакого дублирования в Rust-памяти. AFTER
DELETE-триггер `chunks_vec_ad` каскадно сносит строки из vec0 при
удалении из `chunks` (которое в свою очередь триггерится `ON DELETE
CASCADE documents → chunks`).

### Подключение `sqlite-vec`

Регистрация — глобально, через `sqlite3_auto_extension` (one-shot
в процессе), делается из `synthos::run_desktop` (`lib.rs`):

```rust
kb::init_sqlite_vec();
```

Без feature `kb-sqlite-vec` функция no-op'ом возвращается, флаг
`is_sqlite_vec_registered()` остаётся `false`, и все `VectorIndex`
деградируют в `Scan`.

Сборка:

```sh
cargo build -p synthos --features kb-sqlite-vec   # bundled extension
cargo build -p synthos --no-default-features      # только scan
```

### Дистанция и совместимость интерфейса

vec0 хранит L2² (по умолчанию). Для unit-vector'ов (которые у нас
лежат после `Embedder.encode`) выполняется `cos = 1 − L2²/2`, и мы
конвертируем при выдаче наружу — `Store::vector_search` возвращает
тот же `Vec<(i64, f32)>` с «больше = лучше», независимо от backend'а.
RRF в `hybrid_search` инвариантен к этой замене, поскольку использует
только rank, а не сам score.

### Миграция существующих коллекций

При повторном `Store::open` коллекции, у которой `chunks` уже заполнены,
а `chunks_vec` ещё нет, выполняется `VectorIndex::reindex_all` —
embedding'и перекачиваются в vec0 in-place. Идемпотентно: повторные
запуски `reindex_all` не дублируют строк.

## Источники документов

- **Файл**: `.md`/`.markdown`/`.txt`/`.html`/`.htm`/`.pdf` + код-файлы
  (`.rs`/`.py`/`.json`/...). Markdown — через `pulldown-cmark`,
  HTML — через `htmd`, PDF — через `pdf-extract`.
- **Папка**: рекурсивный walk с уважением `.gitignore` (`ignore` crate)
  + дефолтный blacklist (`target/`, `node_modules/`, бинарные расширения).
- **PDF**: отдельный вариант (если расширение не `.pdf`).
- **URL**: shared helper `chat::tools::web_fetch::fetch_url` —
  `web_read` tool и kb-ingest используют один путь.

## CPU / GPU

Отдельных feature-флагов нет: ядра CUDA в сборке всегда, устройство выбирается
в карточке «Модели» (`embedder_device` / `reranker_device`; на GPU dtype F16,
на CPU F32). Смена устройства выгружает модели — следующая надобность
поднимет их на новом.

## Auto-augment system prompt

> **Статус (26.09.2026, вечер): подключено заново, по-другому.** Тумблер
> «Подмешивать найденное в вопрос» (Настройки → Базы знаний, карточка моделей;
> `kb.auto_augment` → `auto_augment_default`). В начале агентского цикла
> (`syn_chat::session::kb_augment_block`) — поиск по активным коллекциям чата и
> блок `=== Knowledge base context … ===` в КОПИЮ текущего сообщения
> пользователя, не в системный промпт: префикс истории не меняется, префикс-KV
> цел, лента чата не трогается. Бюджет — `augment_token_budget`, top-K —
> `default_top_k`. Ниже — описание прежней реализации старого чата (до 8bda282).

Async pre-step в `chat::session::start_agent_turn`: до спавна `run_agent`
синхронно собираем RAG-блок и подмешиваем его в system prompt между
ACTION_RULE и user_system_prompt.

**Триггер:** `kb.auto_augment && !active_in_chat_ids.is_empty() && last_user_text != ""`.

**Поток:**
1. `start_agent_turn` снимает snapshot (`auto_augment`, `active_ids`,
   query из последнего user-сообщения через `find_last_user_before`,
   `kb_cfg.default_top_k`, `kb_cfg.augment_token_budget`).
2. Чистится `chat.augment_text` (атомарно с прочим per-turn-state),
   ставится `kb.augment_in_progress=true`.
3. `spawn(async { ... })`:
   - `kb::augment::compute(&query, top_k, token_budget).await`:
     `snapshot_from_main()` → `tokio::task::spawn_blocking { per-коллекция Store::open + hybrid_search → merge/sort/truncate → format }`.
   - На main: `kb.augment_in_progress=false`, при успехе `chat.augment_text.set(text)` (если abort не bumped).
   - При `Err`: `log::warn!` + `notifications.warning(e.user_message())`.
4. После phase 1 — обычный `run_agent(...)`.
5. `build_history_from_slice_at` читает `chat.augment_text` untracked'ом
   и вставляет блок в system prompt.

**Сигнатура:**
```rust
pub async fn compute(
    query: &str,
    top_k: usize,
    token_budget: usize,
) -> Result<String, AugmentError>;

pub enum AugmentError { NoEmbedder, NoCollections, Spawn(String) }
```

**Формат augment-блока:**
```
=== Контекст из базы знаний (источник для ответа, не пересказывай дословно) ===

[1] [Имя коллекции] Заголовок документа:
<до 800 символов из chunk.text>

[2] [Коллекция-2] Документ:
<...>

=== Конец контекста ===
```

**Error handling (degradable):**
- `NoEmbedder(причина)` → warning toast с причиной (бандл не найден / ошибка загрузки). Незагруженная модель — не ошибка: augment поднимает её сам.
- `NoCollections` → тихо (chip покажет «Базы знаний» приглушённо).
- Ошибка на одной коллекции → `log::warn!` + пропуск, остальные продолжают.
- Abort посреди compute → проверка `abort_snapshot` перед `set augment_text` — bumped значит не выставляем; `augment_in_progress` гасим (в т.ч. в `abort()`).

**Lifecycle `augment_text`:**
- Создаётся в `ChatCtx::new` пустым.
- Сбрасывается в начале каждого `start_agent_turn` (единая точка вместо трёх).
- Сбрасывается при `registry::select_internal` (переключение чата — иначе augment чата A попадёт в первый ответ чата B).

**Сигналы в KbCtx:**
- `auto_augment: RwSignal<bool>` — флаг включения (значение тогглится popover'ом или Settings).
- `augment_in_progress: RwSignal<bool>` — индикатор «Поиск в KB…» в input-toolbar.

## KB chip в chat input panel

Multi-select коллекций знаний для текущего чата прямо из input-панели,
без захода в Settings. Реализован как `components/kb_chip.rs` + Portal-popover.

**Расположение в toolbar input-панели** (`components/input_panel.rs`):
left-Row порядок — `attach | format(5) | mic | kb_chip | augment_progress | video`.

**Chip-кнопка:** GestureDetector → DecoratedBox с иконкой `MI_MENU_BOOK` и
текстом `Базы: N` (или «Базы знаний» приглушённо при N=0). Клик
тогглит `kb.kb_chip_open`.

**Popover** (монтируется в `pages/chat::view()` рядом с `tool_confirm::view()`,
чтобы Portal имел Stack-родителя для backdrop):
- `Portal::new().is_open(kb.kb_chip_open).modal(true).backdrop(true).anchor(PortalAnchor::BottomStart { margin_bottom: 96, margin_left: 280 }).width(380)`.
- Header (название + close `MI_CLOSE`).
- Checkbox «Auto-augment system prompt» — двусторонняя связка с `kb.auto_augment`.
- ScrollView со списком всех коллекций registry: Checkbox + name + «N док · M чанков». Клик по любой части row → `toggle_in_chat(id)`.
- Footer: «Открыть настройки» → переключает route на `settings/knowledge_base`.
- Empty state (registry пуст): hint + та же кнопка «Открыть настройки».

**Стили:** `styles/components/kb_chip.mss` — chip + popover + pulse-keyframe
для индикатора augment. Подключены в `src/styles.rs` после `input_panel.mss`.

**Сигналы:**
- `kb.kb_chip_open: RwSignal<bool>` — состояние popover'а (KbCtx, не локальный signal, потому что триггер chip'а и тело Portal'а монтируются в разных узлах дерева).
- `kb.active_in_chat_ids: RwSignal<Vec<String>>` — multi-select (общий с `kb_search` tool'ом и `kb::augment::compute`).
