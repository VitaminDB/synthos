# Qwen3.8-Flash-Next (Qwen4Exp): скорость префилла и декода на длинном контексте

Дата: 10.09.2026. Бандл `qwen3.8-flash-next.syn` (121 ГиБ: эксперты NVFP4
64,7 ГБ = 48 слоёв × 512 экспертов × 2,64 МБ; таблицы n-грамм MXFP8 50 ГБ;
резидентные веса 4,5 ГБ). Карта RTX 5090 Laptop 24 ГБ, RAM 93 ГБ, NVMe
5,3 ГБ/с. Сценарий пользователя: чат с историей ≈100k токенов, каждый ход —
хвост промпта в несколько тысяч токенов плюс декод.

## Что было (журнал чата 07.09, контекст 46k–81k)

| Этап | Было |
|---|---|
| Полный префилл 67k | 100 с (670 ток/с) |
| Хвост хода 3–5k (префикс-KV) | 8,2–10 с (500–600 ток/с) |
| Декод при 50–80k | 8–10 ток/с |

Профиль декода (1k контекст, 200 токенов, кэш экспертов 10 ГБ): 96 мс на
токен, из них **75 мс — подкачка экспертов** (≈240 промахов на токен по
2,64 МБ = 630 МБ, путь «страничный кэш → memcpy в pinned-буфер → DMA» давал
8,5 ГБ/с). Остальное: linear_attn 10 мс, hyper-connections 6,6, QSA 5,
PLE 2,6, GEMV экспертов 3,3, роутер 2. По nsys — ≈5000 запусков ядер на
токен, карта занята ≈30 % времени.

Префилл 8k (одним чанком): 87 % времени MoE — та же подкачка всей стопки
(65 ГБ) на каждый чанк; при контексте >16k работает послойный проход
(`prefill_by_layers`), но кэш экспертов после OOM-`reclaim` ужимался до 1 ГБ
(меньше слоя, 1,35 ГБ) и стопка перечитывалась на каждый чанк.

## Что сделано (synaptix `41ddac6` и далее)

### 1. Pinned-зеркало экспертов в RAM

`cuMemHostRegister(READ_ONLY)` на страницы mmap бандла на этой платформе не
поддержан (`CUDA_ERROR_NOT_SUPPORTED`, атрибут
`READ_ONLY_HOST_REGISTER_SUPPORTED = 0`; бенч
`synaptix-core/tests/zz_hostreg_bench.rs`). Поэтому — копия: при загрузке
модели `Qwen4ExpPipeline` поднимает `OffloadPinCacheGuard::new_pooled` над
диапазонами `.qpacked`/`.qscales` всех стопок экспертов (192 диапазона),
четыре копировщика фоном, бюджет `SYN_QWEN4EXP_HOST_MIRROR_GB` (0 —
выключить; по умолчанию `MemAvailable − 10 ГБ`, влезло 63,3 ГБ целиком).
Скопированные страницы mmap отдаются системе (`MADV_DONTNEED`), так что
RAM в сумме растёт лишь на то, чего в страничном кэше не было. Пока диапазон
не догнан водяным знаком, подкачка идёт прежним путём.

Подкачка стала прямой DMA: 72 тыс. экспертов за 4,7 с вместо 15,0 (39 ГБ/с).
Цена — 63 ГБ RAM закреплены на всё время жизни модели. Копировщики стартуют
после загрузки весов (иначе чтение бандла отнимало NVMe у загрузки: 3 → 21 с)
и заполняют зеркало за ≈17 с фоном; диапазоны нарезаны кусками ≤64 МБ, чтобы
`cuMemHostAlloc` не держал драйверную блокировку сотни миллисекунд.

### 2. Эксперты в зеркале лежат перемешанными

Все NVFP4-ядра GEMV/GEMM читают «перемешанную» раскладку
(`nvfp4_w_repack`: тайлы 16 строк × 64 значения); исходный packed после первого
умножения всё равно освобождается. Раньше каждая подкачка стоила ещё ядро
перепаковки, вторую аллокацию и освобождение (по два на эксперта — 480 ядер
на токен). Теперь копировщики зеркала перепаковывают матрицы на хосте
(`QuantWeight::nvfp4_repack_host`, паритет с ядром — тест
`nvfp4_repack_host.rs`), `build_quant_slice` видит помеченный диапазон
(`offload_pin_resolve_tagged`) и собирает `QuantWeight::from_shuffled` одной
DMA. Декод 20,6 → 22,2 ток/с.

### 3. Слитые ядра декода (`cu/fused/qwen4_decode.cu`)

- `group_rms_f16` — групповой RMS одним ядром вместо ~10 (hyper-connections
  ×2 на слой, PLE ×3);
- `hc_mix_f16`, `hc_inject_f16`, `scale_act_f16` — смешивание потоков
  gated-residual и впрыск блока;
- `weighted_rows_sum_f16` — сборка выходов экспертов с весами роутера;
- декод-шаг GDN через существующий слитый путь `linear_attn_decode_step`
  (conv-update + prep + gated delta rule + RmsNorm·гейт) — добавлен режим
  `sigmoid(z)` вместо `silu(z)` (у Qwen4Exp `output_gate_type = sigmoid`);
  раньше один токен шёл через чанковый скан (bmm по 64×128 на голову,
  ~250 `bmm_f32` на токен).

Выключатель для A/B — `SYN_QWEN4EXP_FUSED=0`. Без профиля: 17,8 → 20,6 ток/с.

### 4. Групповой GEMM экспертов на префилле с кэшем оффлоада

`forward_chunk_segmented` (путь Gemma-4: один `gemm_grouped` на слой по
таблице адресов) был выключен при `cache.is_some()`. Теперь эксперты берутся
из кэша по `Arc` группами по `SYN_MOE_GROUP` (128 ≈ 340 МБ) — промахи группы
поднимаются параллельно, `Arc` держит их живыми на время GEMM. Вместо ~5
запусков на эксперта (24 576 экспертов на проход) — 4 группы на слой.
Префилл 8k: 17,3 → 5,9 с; хвост 3k: 8–12 → 3,2 с.

### 5. Бюджет VRAM вокруг префилла

- Резерв послойного префилла учитывает поток всех токенов хвоста
  (`activation_reserve_prefill`): иначе OOM посреди слоя → `reclaim` → кэш
  1 ГБ → стопка перечитывается на каждый чанк (80k: подкачано 101 тыс.
  экспертов вместо 25 тыс.).
- После префилла пул активаций тримится до `fit_to_vram`: после 80k кэш
  замирал на 5 ГБ при потолке 12 (слабина пула считалась занятой), теперь
  9,5 ГБ.

### 6. Вытеснение из кэша экспертов — по жару slab'а

Арена отдаёт драйверу только slab целиком, и жертвой был самый старый slab —
горячие эксперты из него перечитывались каждые несколько токенов. Теперь у
резидента счётчик обращений (`heat`, затухает вдвое на каждом четвёртом
проходе), а уходит slab с наименьшей суммой. A/B на декоде 1k/200 токенов
(кэш 10 ГБ): по возрасту — 72,1 тыс. подкачек, 21,3–21,5 ток/с; по жару —
65,2 тыс., 22,4–22,6 ток/с. Старое поведение — `SYN_EXPERT_EVICT=age`.

## Замеры (бенч `crates/synaptix/tests/qwen4exp_bench.rs`)

Сценарий как в чате: история N токенов, ходы с префикс-KV, хвост 3074
токена, 64 токена декода. Кэш экспертов 12 ГБ на 80k, 10 ГБ на 1k.
`SYN_QWEN4EXP_PROFILE=sync` завышает время (синхронизация на каждом этапе).

| | Было (журнал 07.09) | Стало |
|---|---|---|
| Полный префилл 80k | ≈100 с на 67k | 45,4 с (1760 ток/с) |
| Хвост 3k при 80k | 8,2–10 с | 3,3 с (930 ток/с) |
| Декод при 80k | 8–10 ток/с | 17,5–18,4 ток/с (с sync-профилем) |
| Декод при 1k (200 ток) | 10,3 ток/с | 22,5 ток/с |
| Загрузка модели | 3 с | 2,5 с (+17 с фонового заполнения зеркала) |
| Префилл 8k одним чанком | 17,3 с | 5,9 с |

Расклад полного префилла 80k теперь (45 с): QSA 17,6 с (ядро по таблице
блоков 13,1, индексатор 3,5), linear_attn 14,7 (чанковый скан 11,9), MoE
10,7, hyper-connections 1,6, PLE 1,5. То есть дальше — ядра внимания
(`flash_blocks` в fp8 читает 8 байт на лейн и идёт на ~200 ГБ/с из ~400) и
скан GDN (~1,5 TFLOPS f32).

Расклад хвоста 3k при 80k (3,3 с): подкачка стопки 1,6 с (65 ГБ на 39
ГБ/с — нижняя граница пути), QSA 1,6, linear_attn 0,9.

Расклад декода (45 мс на токен при кэше 10 ГБ): подкачка ≈23 мс (240
промахов), linear_attn ≈8, QSA ≈5, hyper-connections ≈4,5, GEMV экспертов
≈5, PLE ≈2, роутер ≈2. Промахи — главное; в чате кэш до 16 ГБ, промахов
меньше.

## Грабли

- `cuMemHostRegister` на mmap файла не поддержан этим драйвером — только
  копия в `cuMemHostAlloc`.
- `weights_htod` под `ExpertsAllocGuard` шёл мимо арены (прямой
  `cuMemAllocFromPoolAsync`): эксперт не попадал в slab, и учёт
  `fit_to_vram` расходился с реальностью. Теперь — через `alloc_bytes_uninit`.
- Гард зеркала глобален на процесс: `Drop` снимает только свой кэш
  (`Arc::ptr_eq`), иначе гард LTX/Gemma рядом терял бы своё зеркало.
- В `gated_delta_rule.cu` два ядра с одинаковым хвостом сигнатуры — параметр
  `gate_mode` нужно добавлять слитому (`…_fused_rms_norm_f32_to_f16`), а не
  первому попавшемуся.
- Буфер из пула длиннее логического размера (гранулярность аллокатора) —
  паритет перепаковки сравнивать по `n·k/2` байт.
- Профиль MoE (`SYN_MOE_PROFILE`) не синхронизирует поток: `moe:expert` в
  нём — время запуска, ожидание уходит в `moe:prefetch`. Суммы верны только у
  `SYN_QWEN4EXP_PROFILE=sync`.

## Как мерить

```
SYN_QWEN4EXP_BUNDLE=/home/master/Storage/syn_models/qwen3.8-flash-next.syn \
SYN_QWEN4EXP_EXPERT_CACHE_GB=12 SYN_BENCH_CTX=80000 SYN_BENCH_TAIL=3000 \
SYN_BENCH_NEW=64 SYN_BENCH_TURNS=2 SYN_BENCH_WAIT_MIRROR=1 \
[SYN_QWEN4EXP_PROFILE=sync SYN_MOE_PROFILE=1] \
cargo test -p synaptix --release --test qwen4exp_bench -- --nocapture --test-threads=1
```

`SYN_BENCH_WAIT_MIRROR=1` ждёт заполнения зеркала перед первым ходом (тёплый
замер подкачки). Профили печатаются на каждый ход.

## Что не сделано

- Ядра длинного префилла: `flash_blocks` fp8 (16 байт на лейн), скан GDN.
- Перекрытие подкачки со счётом внутри слоя MoE (≤5 мс на токен).
- CUDA-граф декода: роутер MoE читает top-k на хосте на каждом слое, так что
  граф возможен лишь посегментно; хостовой обвязки ещё ≈10 мс на токен.
