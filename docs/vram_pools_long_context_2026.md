# VRAM-пулы и длинный контекст (Qwen3.8-27B на 24 ГБ) — раунд 2026-08-17

Железо: RTX 5090 Laptop 24 ГБ (24463 МиБ), бандл
`/home/master/Storage/syn_models/qwen3.8-27b.syn`, NVFP4-веса, compute F16.
Замеры: `synaptix run … --quant nvfp4 --lm-head-dtype fp8 --embed-dtype fp8
--mtp --temperature 0`, префилл чанками по 256.

## Симптом

Чат в synthos падал на третьем ходу agent-loop'а:

```
Ошибка: forward: model forward: cuda error: alloc chunk_scan ws:
DriverError(CUDA_ERROR_OUT_OF_MEMORY, "out of memory")
```

Панель «Детали» при этом показывала `prompt_tokens 1548` — статистика писалась
только для `turn == 0`, а падало на промпте 6862 токена (web-инструмент дописал
в историю содержимое страниц). Первое, что здесь исправлено, — панель: метрики
теперь пишутся по каждому ходу, `prefill_ms` считается как время до первого
токена (раньше там лежало время планирования ринга, то есть ноль).

## Корень: один async-mempool на веса и на активации

`cuMemPool` устройства настроен с `RELEASE_THRESHOLD=MAX` (иначе под
VRAM-давлением каждая реаллокация активации re-acquire'ит страницы у ОС и
transpose-ядра тормозят в 26 раз). Веса (≈16–18 ГБ резидента), временные
буферы загрузки (bf16-staging по 170 МБ на MLP-вес) и транзиенты префилла
(≈20 МБ трафика аллокаций **на токен**) лежали в одном пуле. Последствия:

* страницу, в которой живёт хоть один вес, `cuMemPoolTrimTo` вернуть не может —
  после загрузки в пуле оседало ~2,4 ГБ нераздаваемой слабины;
* free-list деградировал по ходу префилла: пул прибавлял ~128 МБ на каждый
  чанк из 256 токенов (≈0,5 МБ на токен промпта) при **неизменном** `used`;
* на 8k токенов промпта пул упирался в потолок карты: `reserved 24,5 ГБ`,
  `used 17,9 ГБ`, свободно по драйверу 30 МБ — и аллокация скретча в 6 МБ
  падала с OOM. Никакой `trim` (даже sync всех стримов + `trim_to(0)`) не
  возвращал ни байта.

Диагностика воспроизводится однострочником:

```
SYN_TRACE_PREFILL_MEM=1 synaptix run … --prompt-file p8k.txt
# [PREFILL_MEM] 2816/8325 ток: free=2237 MB, default rsv=21184/17377 MB …
# [PREFILL_MEM] 6656/8325 ток: free=93   MB, default rsv=23328/17378 MB …
```

`SYN_TRACE_PREFILL_MEM=trim` дополнительно делает sync+hard-trim после каждого
чанка и печатает, сколько удалось вернуть (в старой схеме — ноль).

## Что сделано

### synaptix: три пула вместо одного

`synaptix_core::device::cuda`:

* **default-пул** — веса и долгоживущие кэши ядер (shuffled-веса NVFP4,
  MXFP8-скретчи, [`WsBuf`]-скретчи оркестраторов). Стабильная карусель
  size-класcов, churn'а нет.
* **пул активаций** (`activations_pool`) — всё, что живёт один forward:
  выходы операций, KV-ринг, скретчи ядер на вызов. Между чанками он пуст,
  поэтому и не деградирует, и триммится целиком.
* **staging-пул** (бывший `weights_pool`) — байты весов на загрузке
  (`alloc_bytes_uninit`). У квантованных моделей это временные bf16-буферы;
  `WeightsAllocGuard::for_device` на выходе из загрузки тримит пул и отдаёт
  драйверу всё сразу — это те самые +2,4 ГБ, которых потом не хватало рингу.

Маршрутизация: `CudaBackend::alloc_zeros/alloc_uninit` и `Tensor::zeros` →
пул активаций; H2D-байты → staging (под загрузкой) или активации; скретчи ядер
→ `WsAlloc::ws_alloc_*` (активации) либо `WsAlloc::cache_alloc_*` (default,
для кэшей между вызовами). Под `cuStreamBeginCapture` — всегда default-пул
(аллокации становятся узлами графа). Аварийный выключатель: `SYN_ACT_POOL=0`.

Трим на OOM теперь идёт по всем трём пулам (`cuda_pool::trim_pools_on_oom`), и
скретчи ядер, которые раньше брались у cudarc напрямую и потому не имели
страховки, получили её (`WsAlloc` с sync+trim+5 ретраями и диагностикой
`[WS_OOM]`).

### synaptix: префилл full-attention гибрида на FA-4

`FullAttn::forward` при `T>1` отдавал `flash_attention` narrow-вьюхи KV-кэша,
та отвечала `NonContiguous`, и путь скатывался в split-K decode-ядро (для
`Tq=256` оно же аллоцирует partials размером `nh×Tq×splits×d` — до 160 МБ на
слой на чанк, растущие с позицией). Теперь при `T>1` на CUDA и F16/BF16-KV
зовётся `flash_attention_prefill_dev` (Q-тайлинг, читает preallocated KV как
есть, активная длина — device-скаляр). Побочно исчез главный источник роста
пула.

### synaptix: скретчи оркестраторов GDN — кэш вместо 38k аллокаций

`chunk_gated_delta_rule` брал 14 свежих буферов, `linear_attn_chunk_prefill` —
ещё 8, и так на каждый из 48 linear-слоёв каждого чанка. Теперь это `WsBuf`
на устройство: размер под запрос ровно (часть ядер выводит геометрию из
`slice.len()`), содержимое зануляется — семантика `alloc_zeros` сохранена,
аллокаций после первого чанка нет. Освобождаются в `release_device_caches()`.

### synaptix: MXFP8-KV стал доступен фасаду, а счётчик — честным

* `KvDtypePolicy::MXFP8` (имена `fp8e4m3` / `fp8` / `mxfp8`): дропдаун
  «KV-cache dtype → FP8 E4M3» в настройках synthos раньше молча откатывался в
  F16, потому что `from_name` такого варианта не знал.
* `kv_bytes_per_token` для MXFP8 считал 2 байта на элемент (как F16) вместо
  «байт + E8M0-масштаб на блок из 32» — бюджет контекста выходил вдвое меньше
  реального. Теперь 33 КиБ/токен против 64 КиБ у F16.

### synthos: планировщик ринга и честная панель

`syn_chat::session`:

* `RingPlan` — ринг считается как `промпт + min(max_new_tokens, 8192) + 128`,
  округляется вверх до 4096 (ход за ходом ринг одного размера → блоки пула
  переиспользуются) и ограничивается бюджетом VRAM с запасом 3 ГБ (активации
  префилла ≈0,8 ГБ + ленивые кэши ядер ≈1,1 ГБ). Раньше ринг планировался на
  `max_new_tokens` со слайдера — 28k токенов ответа, то есть 2,3 ГБ KV впустую.
* OOM больше не убивает ход: до трёх повторов с вдвое меньшим бюджетом ответа
  (и только пока не отдан ни один токен), с `log::warn` и очисткой стрима.
  Обрыв генерации теперь пишется в лог (`log::error`, раньше `eprintln!` — в
  файл лога не попадал).
* Панель: `prompt_tokens`/`prefill_ms` по каждому ходу, плюс строки «ходов
  agent-loop», «KV-ринг» (токены и МБ), «контекст по VRAM», «VRAM свободно».
  При загрузке модели в лог пишется потолок контекста по памяти.
* `vram_available_mb` учитывает слабину всех трёх пулов.

## Сколько контекста влезает

KV на токен у Qwen3.8-27B (16 full-attention слоёв × 4 KV-головы × head_dim
256 × K и V):

* F16 — **64 КиБ/ток**;
* MXFP8 — **33 КиБ/ток** (байт + масштаб на 32 элемента).

После загрузки (веса NVFP4, lm_head+embed FP8) свободно ≈4,8 ГБ; на первом
forward'е ленивые кэши ядер забирают ещё ≈1,1 ГБ, так что рингу достаётся
≈4,2 ГБ. Замеренный потолок:

| KV dtype | Потолок контекста | Скорость на 8k |
|---|---|---|
| F16 | ≈65–68k ток | prefill 1476 ток/с, decode 36,7 ток/с |
| MXFP8 | ≈128k ток | prefill 870 ток/с, decode 11,9 ток/с |

То есть **80k токенов требуют MXFP8-KV** (Настройки → AI Models → KV-cache
dtype → FP8 E4M3): при F16 не хватает ~1 ГБ. Обратная сторона — MXFP8-декод
пока медленный и деградирует с длиной (1,2 ток/с на 80k против 12 на 8k):
`flash_attention_mxfp8kv` на `Tq=1` не делает split-K, а Q-тайлового
MXFP8-префилла нет вообще, поэтому префилл на MXFP8 в 1,7 раза медленнее F16.

## Что осталось

1. **Split-K для MXFP8-декода** и Q-тайловое MXFP8-префилл-ядро — снимут
   плату за длинный контекст (сейчас это главная причина, по которой 80k
   «влезает, но неудобно»).
2. **Префикс-KV между ходами.** `HybridPipeline::generate_streaming_resume` и
   `generate_with_graph_resume` уже умеют продолжать с `kv.seq_len`, но фасад
   их не отдаёт, и synthos на каждом ходу префиллит всю историю заново. На 80k
   это ~10 минут на ход — практически это и есть настоящий потолок
   удобного контекста, а не VRAM.
3. **1,1 ГБ фрагментации на первом forward'е**: shuffled-веса NVFP4 строятся
   лениво (`shuffled_or_try_init` + `release_packed`), и своп «выделить shuf →
   освободить packed» оставляет в default-пуле дыры. Строить shuf на загрузке
   (внутри `WeightsAllocGuard`) вернуло бы ещё гигабайт под контекст.
4. `mxfp8_linear_shapes` красный и **до** этих правок (L2 0,183 при пороге
   0,1 на выровненном N; незакоммиченная работа по декванту полосой добавила
   расхождение и на невыровненном: 0,0998 → 0,1818). К пулам отношения не
   имеет — проверено `SYN_ACT_POOL=0`.

## Инструменты диагностики

| Переменная | Что делает |
|---|---|
| `SYN_TRACE_PREFILL_MEM=1` | по чанкам печатает free/rsv/used всех пулов; `=trim` — ещё и sync+hard-trim с замером отдачи |
| `SYNAPTIX_TRACE_ALLOC_MIN=<байт>` | печатать каждую device-аллокацию не меньше порога (и тензорные, и скретчи ядер) |
| `SYNAPTIX_TRACE_ALLOC=<байт>` | backtrace на аллокацию точного размера |
| `SYN_ACT_POOL=0` | вернуть один общий пул (старое поведение) |
| `SYN_PREFILL_CHUNK=<N>` | перебить размер чанка префилла |
| `[WS_OOM]` / `[OOM_TOP]` | автоматический дамп живых size-класcов и статистики пулов при исчерпании VRAM |
